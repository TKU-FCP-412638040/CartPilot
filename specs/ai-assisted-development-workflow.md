# AI 協作開發工作流

## 背景與目的

讓 AI 協助 CartPilot 從需求到驗收，縮短交付時間，同時讓每個變更可追溯、可驗證、可由專案負責人理解。AI 工作使用 GitHub Copilot cloud sandbox，檢查使用 GitHub-hosted Actions；不要求本機服務或命令。CI 已設定 lint/build，但 Jira connector、repository ruleset 與部署尚須管理者在雲端服務設定。

## 範圍

- 將每個工作項目從規格、設計、實作、檢查到產品驗收串起來。
- 讓 repo 內的 AI 助理能先載入專案脈絡與不可違反的規則。
- 建立每個 PR 都能使用的驗證與回饋清單。
- 雲端服務、權限與整合操作依 [雲端 AI 工具整合規格](./ai-tooling-integrations.md)。
- 定義 Jira、額外 Skills、Hooks、MCP 等尚未設定工具的接入原則。

## 工作流程

1. **選定工作項目**：由人決定優先順序，或從已核准的 backlog 挑選；確認範圍與負責人。
2. **需求與規格**：AI 閱讀現有規格、相關程式與決策卡。新功能或行為改變先更新 `specs/`，列出範圍、非目標與可驗收條件；不清楚的產品行為先詢問，不自行補成既定需求。
3. **Domain / 軟體設計**：AI 說明 domain 規則、資料流、模組與錯誤情境。跨模組或高風險變更提供簡短設計記錄；重要取捨先新增 `decisions/` 決策卡。
4. **拆解與追蹤**：把驗收條件拆成可獨立驗證的小任務。若 Jira read-only connector 已設定，AI 可讀取票單；未設定前以規格、GitHub issue 與 PR 作為追蹤依據。AI 可草擬 Jira 內容，寫入權限需在確認可強制執行核准前保持關閉。
5. **實作與 feedback loop**：AI 一次處理一個可驗證切片，先寫或更新測試，再實作。執行最小相關檢查；失敗時保留錯誤、修正根因、重跑失敗檢查及受影響的檢查。若驗收條件不符或需求有歧義，停下來回報。
6. **變更檢查**：AI 檢查 diff、規格覆蓋、資料與權限邊界、錯誤處理及回歸風險。高風險或跨域變更使用獨立 reviewer；reviewer 不得只確認實作者自己的摘要。
7. **提交與 PR**：雲端 Agent 準備變更與 PR，連結規格與工作項目，列出實際執行的檢查與結果。是否送出外部寫入操作由人控制；不得自動合併。
8. **產品驗收與回饋**：依規格逐項驗收。UI 變更需在實際畫面確認主要流程與錯誤狀態；涉及金錢、權限或資料寫入時，使用自造資料並驗證拒絕路徑。把發現的缺陷修回同一回饋迴圈；重複失敗模式更新規格、評估題或 repo 指引。

## 驗證門檻

- 每項變更都能指回規格或明確標示為不改變行為的維護工作。
- 每個驗收條件都對應測試、評估題或明確的人工檢查步驟。
- AI coding session 於 GitHub Copilot cloud sandbox 執行，CI 於 GitHub-hosted Actions 執行；不要求本機服務或命令。
- 前端變更至少通過 `cd frontend && npm run lint` 與 `cd frontend && npm run build`；GitHub Actions 另執行 `node --test .github/scripts/create-jira-issue.test.mjs`。
- AI 回答品質或政策行為變更，更新 `evals/` 評估資料並執行評估；未有評估執行器前，需列出人工評估步驟與結果，不得宣稱自動評估通過。
- PR 必須列出實際執行的驗證、結果，以及尚未完成的驗收項目；未通過或未說明的門檻不得標示完成。
- 退款、訂單或其他資料寫入不得由 AI 自動執行；操作前必須取得人工確認，驗證時只用自造資料。

## 不做什麼

- 不要求每個簡單變更都建立冗長設計文件或額外 reviewer。
- 不在未設定憑證與最小權限前自動寫入 Jira；不得自動合併或部署 Production。
- 不以 PR 數量取代品質指標，也不承諾固定每日產量。
- 不把未實際執行的測試或產品檢查寫成已通過。

## 驗收標準

1. 新功能流程要求先有規格和可驗收條件，再開始改程式。
2. AI 助理可從 repo 指引得知 CartPilot 的產品脈絡、資料安全原則與必要驗證命令。
3. 工作流程明確指出需求釐清、重要決策、失敗回饋及外部寫入的人工確認點。
4. PR 範本要求連結工作規格、列出驗收結果、測試結果、產品檢查與未完成事項。
5. 文件清楚區分 cloud sandbox、GitHub-hosted Actions 與未設定的外部服務；已加入的 repo workflow Skill 應有實際檔案可查。
6. 現有功能行為與應用程式碼不因本工作流文件而改變。

## 開放問題

- 是否採用 Jira 及其專案／欄位／狀態對應方式。
- 是否建立正式 AI 評估執行器，以及可接受的品質門檻。
- 是否新增更多專用 Skills，或接入 CI、Hooks、MCP；需另行評估權限、維護成本與核准流程。
